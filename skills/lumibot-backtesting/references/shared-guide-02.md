## Data and platform failures during unfinished validation

A supported strategy's failed first validation remains active work when the
failure is in a provider or platform dependency. Inspect the concrete terminal
error and saved revision. Missing auxiliary metadata, including corporate-action
coverage, does not prove missing credentials, an unsupported instrument, or an
unavailable primary price series. Generic fallback labels such as
`failureOwner="strategy"`, `failureCategory="strategy_or_runtime"`, or an
unexplained `retryable=false` do not override concrete runtime evidence.

When the supported path has no proven credential, entitlement, required-data
integrity or compatibility blocker, no validation is already running, and the
attempt budget remains, perform one bounded availability retry on the unchanged
saved revision. A data retry requires no code edit or new revision; this
exception overrides the edit-then-retest sequences below. Preserve the selected
instrument, provider, strategy rules, sizing and execution behavior. Do not ask
the user to select another provider or approve that routine retry.

Copy the failed run's exact start and end dates into the retry. Do not apply the
initial first-test window chooser again, convert a calendar window to a shorter
Monday-through-Friday interval, or substitute another recent week. Only concrete
window-availability evidence or the user's changed mandate can justify different
bounds; a metadata failure supplies neither.

Record the returned external wait on the visible plan. The first build is still
unfinished until terminal validation succeeds. If the same platform prerequisite
persists after the bounded retry and no concrete recovery is available, record
that persistent blocker with the executed retry evidence. Genuine missing
credentials, entitlements, unsupported inputs, explicit user stops, exhausted
attempt budgets and duplicate active runs retain their existing stop boundaries.

Decision-time wake checklist:
- If the wake says `completed_no_trades`, raw `completed` with `tradeCount=0`, `resultClassification="no_trades"`, `firstCycleOutcome="no_trades"`, `failed`, `terminated_timeout`, `timed_out`, or another terminal non-success, this turn is a rescue execution turn. It is not a final report turn. Apply the timeout override first; timeout rescue starts with runtime diagnosis, not no-trade rule changes.
- If there is no active plan item, create or repair visible plan state, then continue rescue. The hook evidence is not dependent on having a perfect plan already.
- If a plan tool fails, read the exact error text. When it returns unresolved unsuccessful/partial attempt ids, retry with `item.dependsOnItemIds` containing every listed id, or call `replace_plan_items` once to reconcile the full visible plan. Do not keep alternating one id at a time.
- After the plan has an `in_progress` rescue item, the next step is `get_file` or another visible evidence/edit tool, then a file edit that returns a new revision, then `start_backtest`. Final prose is invalid before that sequence unless you recorded a real blocker, user stop, or attempt budget exhaustion with plan tools.
- A failed `query_csv`, missing artifact, stale edit handle, or failed plan mutation is normal recovery feedback. Correct the shape/handle or use the available terminal hook evidence and keep moving.

Mandatory action rule:
- In repair mode, diagnosis-only is not a completed rescue when you can name a concrete fix. If logs/artifacts/code show a fixable cause, create a normal corrected revision with file tools in the same rescue turn, then call `start_backtest` on the new revision over the first-test window (see First test window below).
- For a localized runtime error such as one bad attribute or helper call, prefer `patch_file` against the `get_file` edit handle. Preserve the rest of the runnable file, especially its `if __name__ == "__main__"` backtest/live runner. Do not replace the whole file with only the strategy class. If an edit result reports blocked execution readiness or `MISSING_RUNNER`, repair that readiness issue and read back the next revision before calling `start_backtest`.
- For `ModuleNotFoundError` or another missing-package import failure, read both the saved `main.py` and `requirements.txt` before editing. If the imported third-party package is absent, add it with an exact public PyPI `==` pin, read `requirements.txt` back, and start the next smoke on the returned revision. Preserve the failed run's date bounds when available; otherwise choose the first-test window below. Repairing an import or plotting dependency does not justify expanding that window. Use `replace_file` when `requirements.txt` is empty; use a bounded `patch_file` or complete replacement when it is populated. Preserve every required strategy capability and make the smoke exercise the import path. Do not wrap the import in a fallback, make it optional, or delete the dependent feature just to make startup pass.
- If the exact dependency is already present in the saved `requirements.txt` and the run still reports that it cannot be imported, classify that as a platform installation or interpreter defect rather than generated strategy logic. Preserve the files, inspect the runtime logs and package-install evidence, and report the product defect. Do not keep rewriting valid dependency declarations or the user's strategy to hide the platform failure.
- Zero-trade cause order (apply before any edit, rule proposal, or approval request): (1) window too short, (2) code bug, (3) data missing, (4) rules never fire or conflict. Check (1) first from the run's start/end dates and the saved cadence: when the run is shorter than the First test window below for this strategy's decision cadence (for example a 7-day run of daily-bar rules, or any run too short for the rule to plausibly fire), the window is the cause. Do not edit code, do not propose a rule change, and do not ask permission. Read the saved file, then call `start_backtest` on the same saved revision over a longer window chosen by the First test window reasoning below (cost limits plus a plausible chance to trade), record the wait (copy the returned `externalWaitId` exactly; only one plan item may be `in_progress`, so complete the diagnosis item before or in the same update that starts the rerun item), and tell the user in plain words that the earlier test was too short for their rules and which period is running now. Only when the window was already adequate do causes (2) to (4) apply as described below. A user question such as "what happened?" or "why no trades?" during this first test does not stop the loop: for causes (1) and (2), answer in plain words and also make the fix and rerun in the same turn, without asking first.
- Required no-trade wake continuation sequence: for first-cycle `completed_no_trades`, raw `completed` with `tradeCount=0`, `resultClassification="no_trades"`, or `firstCycleOutcome="no_trades"`, complete the terminal validation attempt as `outcome.status="unsuccessful"` with source evidence, then inspect the saved code and existing backtest tools for the exact cause. When `get_file` is available, read the attached revision with `get_file` before proposing the exact rule change, even when the event payload summarizes the apparent logic. If a technical repair preserves every user rule, create a corrected revision and start the next smoke. If the only available repair changes a signal, threshold, cadence, universe, sizing, risk rule, or option structure, record the rescue item as `waiting_for_user`, propose the exact change, and do not edit or rerun until approved. A proven unsupported dependency or missing external prerequisite is a blocker and stops retries immediately.
- For that no-trade user-decision transition, retain the complete active-plan
  snapshot returned by the latest successful plan tool. After code inspection,
  call `replace_plan_items` once with the full visible list. Preserve existing
  ids, resolve the diagnostic item as partial, and append one waiting approval
  item linked to every unresolved unsuccessful or partial attempt. Never call
  `add_plan_item` before or after this replacement. Do not discover dependency
  ids by trying them one at a time.
- A statement that approval is required is not approval. Unless the current
  user message explicitly supplies the exact replacement threshold, direction,
  cadence, universe, sizing, risk limit, or option structure, do not call a file
  mutation tool. Plan text, an Agent proposal, or an earlier unapproved example
  must never be treated as the user's approval.
- Diagnostic-to-edit cadence: for active first-cycle no-trade rescue, `get_code`, `LumiBot source search`, `LumiBot source read`, `lookup_lumibot_docs`, artifact reads, and log reads are evidence tools, not stopping points. Once you have confirmed zero filled trades and read the saved code, do not spend the rest of the turn summarizing diagnostics. Either use `get_file` plus `replace_file`/`patch_file` to create the next corrected revision and then `start_backtest`, or mark the concrete rescue item `blocked`/`waiting_for_user` with a real blocker. Assistant prose that only reports the diagnostic finding is not an allowed final state. Assistant prose that says "the current rescue step is to broaden/fix the strategy" is also forbidden when the rescue item is still in progress; execute that step with file tools and `start_backtest` in the same turn.
- If any plan tool result says `This plan now contains a completed item with outcome.status="unsuccessful" and no explicit follow-up item`, `Plan item not found`, `Plan items must progress in order`, or `THIS TURN IS NOT COMPLETE`, treat that as a hard continuation instruction. Your next model action must correct the plan state, not summarize. If the error happened because `update_plan_item` or `update_plan_items` targeted a future position, do not target that future position again; those tools update existing rows only. First resolve the current rescue/edit item with `update_plan_item` using the exact current item id from `get_active_plan`, then call `add_plan_item` with a nested `item` object for the new validation wait, or use `replace_plan_items` to represent the full visible list in one mutation. Assistant prose, metric summaries, and final answers are invalid until the follow-up exists and is executed or a real blocker is recorded.
- If the active rescue item is already `in_progress`, that item includes the concrete code edit plus the next `start_backtest` call. Do not mark it completed from diagnosis alone. Do not create or target a future `Start rescue smoke backtest` or `Validate rescue smoke result` row before a file edit succeeds and `start_backtest` returns the new backtest id. If a plan tool says a future position does not exist or plan items must progress in order, treat that as retry feedback: execute the active rescue item with visible file/backtest tools or retry the corrected plan mutation, not assistant prose.
- A file-edit tool only succeeds when its result returns a new revision id/version. If `replace_file` or `patch_file` reports a stale edit handle, EDIT FAILED, or any file-tool error, no new revision exists; treat the tool error as correction feedback, refresh the file/edit handle with `get_file` or `list_files`, retry the edit with the latest returned `editHandle`, and do not call `start_backtest` until a real edit has returned a new revision id.
- After a file edit succeeds, the next validation tool must be `start_backtest` using the returned revision id. Do not call `backtest_status`, `list_backtests`, or any polling/status tool for the new attempt until `start_backtest` has actually returned a new backtest id.
- Only skip file-edit repair plus `start_backtest` when the request is unsupported, a required credential/data entitlement is missing, the user stopped you, the five-backtest-attempt budget is reached, or one concise clarification is truly required before changing intent.
- If a strategy is already attached and the user says "try again", "generate the strategy from the conversation above", "run the smoke backtest", or otherwise asks to rescue/test the same strategy, do not ask them to say "refine it". Treat this as permission to use the attached strategy: inspect the current revision and evidence, edit files if a code change is needed, then call `start_backtest`.
- If a no-trade first-cycle run is blocked by a code-level date gate, contest window check, warmup early-return, or market-session assumption that stops the real strategy logic from ever running, that gate is a code bug: fix the gate so the real rules are evaluated, preserving the user's intended live/contest behavior, and rerun the same window. If the window itself is too short for the rules, extend the window instead of editing code.
- If logs show messages like "outside competition window", "outside contest window", or "staying flat" and the first-cycle smoke has no completed filled-trade result, fix the date gate before rerunning. Preserve the live contest dates, use pre-contest smoke bars for warmup/inspection only, and make sure the actual contest-window iterations can reach the strategy's normal entry logic.
- If a first-cycle smoke fails with `TypeError: 'Bars' object is not iterable`, that is a fixable generated-code/LumiBot API shape error, not a blocker. Do not stop just because `logs.csv` or `errors.csv` artifacts are unavailable; the hook error string is enough evidence. Inspect the saved code, replace direct iteration such as `for bar in bars` or `[bar.close for bar in bars]` with `bars.df` / dataframe column access, create a normal corrected revision, and immediately call `start_backtest` over the same first-test window.
- Do not rescue by adding an unrelated backtest-only validation order, dummy trade, separate backtest-only entry branch, or unapproved simplified or broadened entry path. Do not add branches such as `if IS_BACKTESTING and not traded: buy SPY`.
- Do not use `from __future__ import annotations` or other future imports in rescue-generated strategy files. If a startup failure says a future import is not at the beginning of the file, remove the future import entirely instead of moving it around.
- Do not confuse BotSpot schedule metadata with LumiBot market names. `marketSession: "regular"` and schedule `regular` describe product scheduling only; they are not valid `self.set_market(...)` values. For ordinary US stocks/ETFs, omit `set_market` unless needed, or use a documented LumiBot value such as `"NYSE"`, `"NASDAQ"`, or `"stock"`. Never use `self.set_market("regular")`.
- If docs lookup is unavailable or blocked, continue from the focused skills, artifacts, logs, and code evidence. Do not stop only because a docs lookup failed.

First-cycle smoke rule:
First test window (used whenever the user did not name a backtest length; a user-named length always wins):
- Keep first tests short and fast. Unless the user or a known failed run supplies dates, the default startDate is endDate minus 7 calendar days, with endDate at the latest completed trading day. Use a different length only for the cost or entry-frequency reasons below. An unchanged strategy that can enter during an ordinary week gets this seven-day default after a startup repair too. Warmup history always comes from before the window; never shorten the window, lookbacks, or rules for warmup. A lookback alone is not a reason to add sessions to the validation period: fetch that earlier history before the window, and choose the run length from the entry frequency.
- Adjust the length for what makes a backtest slow or expensive: number of symbols (one symbol is cheap; dozens or 100+ symbols stay at about a week or less), asset type (options are much slower than stocks and ETFs; crypto trades 24/7 so each day holds more data), timeframe (minute and hour bars can be orders of magnitude slower than daily bars, especially on uncached Interactive Brokers data), and, for AI-owned decisions, the model cost per decision (a default model with daily decisions about a week; for an expensive model, explain the cost and use about 1 to 2 days; an explicit choice of that model plus a request to start validation already authorizes that short test, so do not ask for the same choice again).
- A cheap strategy (one or a few stocks or ETFs, daily bars, plain Python) may use about 1 to 3 months when that is what its rules need.
- Before calling `start_backtest`, reason about the rules: will they plausibly trade at least once in this window? Count the bars the window gives at the strategy's cadence and compare with how often the entry can fire (a daily 20/50-day crossover happens only every month or few; a daily RSI dip below 30 a few times a quarter; a 50/200-day cross about once a year). If a trade is unlikely, pick a longer window within the cost limits above. If even that is unlikely, run the affordable window and say plainly, before results arrive, that it may show no trades and why, and offer a longer test.
- The final answer names the window, explains the reason and explicitly states that the user can request a different period, even if an earlier status message already said this. For a longer window chosen because entries are rare, name the actual entry condition and cadence, explain why a week offers too few opportunities, and connect that to the longer period. A plain explanation structure is: "[Named entry condition] is checked [cadence] and may not trigger during a single week; [chosen period] gives it more opportunities. You can request a different period." This required date-control information belongs in the explanation of the chosen run. Do not call it a smoke test.
- Every rerun in the rescue loop uses the same window unless the cause was a too-short window, in which case the rerun uses a longer window chosen by the same cost and plausibility reasoning.
- Bias toward action: when a question is truly needed, ask at most two, each with specific options.
- When you create the first revision for a new strategy, run its first backtest over the first-test window.
- A first-cycle smoke is not successful unless it completes and has at least one filled trade.
- For chartable strategies, a polished first-cycle smoke also needs visible indicator/marker evidence. If a completed filled-trade smoke has no indicator rows or the BotSpot indicators chart is empty, do not assume the product is fine. Load `lumibot-indicators` and, when needed, `backtest-indicator-chart-diagnostics`; read the saved code and inspect `indicators.parquet` / `indicators.csv`. If the saved code computes or trades from chartable prices, entries, exits, stops, thresholds, or indicators but does not call `add_line` and `add_marker`, create a normal new revision that adds those calls and rerun the same first-test window. If the saved code already emits chart data but artifacts/UI are missing it, diagnose the backend/frontend artifact path instead of changing strategy logic.
- Treat failed, timed out, force-stopped, completed_with_errors, completed_no_trades, and raw completed with `tradeCount=0` or `resultClassification="no_trades"` as not done.
- Treat terminal `completed` plus counted filled trades as a first-cycle readiness pass only when the run is not catastrophic. Independently complete the exact Rules review through `strategy-rules`. A filled-trade run can fail Rules, and a compliant zero-trade run can fail first-build readiness. Do not rewrite `rules.json` to erase a failing review unless the user changed intent. A negative return does not invalidate the first-cycle smoke by itself. Negative return, low CAGR, or drawdown can be reported as quality context when no explicit user metric target applies.

- If a strategy has never had a completed filled-trade backtest, failed, timed out, force-stopped, completed_with_errors, and completed_no_trades outcomes are still repair mode even if the current revision number is higher than 1.
- Before the final result or readiness claim, follow the successful-run data-evidence review in `backtest-analysis`: inspect returned data-health/provenance evidence, or use `get_backtest_logs` for this exact run when that evidence is absent. Carry material corporate-action/dividend, price-adjustment or coverage limitations into the explanation; do not change the strategy or rerun merely to erase a warning. If inspection is unavailable, state that specific gap instead of claiming verified data accuracy.
- A failing Rules review and zero filled trades are different failures that can both require repair. Keep their evidence and plan outcomes separate. First-build success requires both a terminal filled-trade readiness pass and, when active Rules exist, an exact passing Rules review.
- Never change the user's rules to make a test trade: no shorter lookbacks, no swapping a crossover for "already above" trend state, no buy-now or first-evaluation activation paths, no wider thresholds, no smaller universe, no dropped confirmations, unless the user says yes to that exact change. A too-short window is fixed by testing a longer window, never by changing rules.
- Never loosen a user constraint to obtain smoke fills without explicit approval. Propose the exact change and reason, mark the rescue waiting for the user, and do not save the change until approved.
- A generated threshold, liquidity filter, spread cap, safety gate, or other
  Agent-invented constraint that is absent from rules.json is not a user Rule.
  If it blocks a required first-build action, treat it as generated-code logic
  to repair, not as a user constraint that requires permission to change. Keep
  genuine execution safety and broker validity checks, but remove or correct an
  invented blocker when the available market data supports the user-requested
  package. Never silently add the invented blocker to Rules after the failure.
- If the user explicitly asks to verify a known defect fix after a prior filled-trade success, help verify with `start_backtest`. Do not shrug with post-success no-auto-rescue policy when the current turn is an explicit verification request for a known bad prior fill.
- Historical filled trades are evidence for their exact revision and window. They do not validate a later saved repair or finish an active authorized build/validation mandate. For that unfinished work, inspect the newest revision and terminal evidence and continue a proven intent-preserving technical repair/retest within the remaining attempt budget, even if `firstCycle=false`. A later completed_no_trades notification after the requested work is complete may be intentional: explain the result without automatically editing or rerunning. Never loosen Rules merely to force a trade.
- If a repair-mode smoke fails or has zero filled trades, diagnose it and continue only while a technical repair preserves user intent. Stop immediately for unsupported input, a required credential or data entitlement, or a user decision on a proposed rule change. The five-attempt budget is a ceiling, not a quota.
- Do not mark the original first-smoke validation item blocked merely because the entry rule never fired. Complete the attempt as `outcome.status="unsuccessful"` and inspect the cause. Continue with an in-progress repair only for an intent-preserving technical fix. Use `waiting_for_user` when a rule change needs approval, and use blocked only for a proven external prerequisite or essential incompatibility.
- If the visible plan already has completed rescue diagnosis/edit/start/validation items and the newest rescue validation also ended `completed_no_trades`, do not consume another attempt automatically. Reuse the existing diagnosis. Apply and validate an intent-preserving technical repair, or record the exact prerequisite, incompatibility, or user approval needed.
- If a terminal no-trade validation item is still waiting, update that same item to `completed` with `outcome.status="unsuccessful"` and source evidence before moving on. Then add a concrete rescue edit/start/validation item or replace the visible list once; do not batch-update that same validation item twice. Do not compensate by adding duplicate diagnosis items. Continue the rescue sequence and move to the next edit/rerun action.
- If a wake says terminal `completed_no_trades`, `get_active_plan` shows a waiting validation item, and `list_backtests`, `query_csv`, or artifacts confirm zero filled trades, that is not a reportable waiting state. Complete that waiting validation item with `outcome.status="unsuccessful"` and source evidence, then add or mark the next concrete rescue edit/start item `in_progress`. Do not create an inspect-only rescue item that can be completed by reading code; the rescue item should require a saved file edit, a new revision id, and a new `start_backtest` call unless a real blocker is proven. Assistant prose that only reports the latest zero-trade metrics is forbidden.
- If a wake says terminal `completed`, `tradeCountStatus="counted"`, and `tradeCount > 0`, while `get_active_plan` still shows a rescue edit item as `in_progress`, the backtest evidence wins over the stale item. Mark the active rescue/validation item completed with `outcome.status="satisfied"` and evidence for the completed filled-trade backtest, then call `complete_plan`. Do not call `get_file`, edit code, or `start_backtest` again just because that stale rescue item was still current.
- In first-cycle repair mode, after `list_backtests` or `backtest_status` confirms terminal no-trade evidence and `get_code` succeeds, inspect logs, trades, statistics, artifacts, provider errors, symbol coverage, and revision linkage as applicable. Then either apply an intent-preserving technical repair and start a new validation, or mark the concrete rescue item `blocked` or `waiting_for_user` for a proven prerequisite, incompatibility, or rule-change decision. Missing one optional artifact is not itself a blocker when other evidence identifies a technical repair.
- If you already marked a rescue item `in_progress` and then called `get_code`, do not end with a vague status report. Continue through an intent-preserving file repair and `start_backtest`, or update the item to `waiting_for_user` or blocked with the exact prerequisite or decision.
- If you have already called `get_code` after a no-trade wake, do not end with a summary headed like "Smoke result", "Evidence", "What happened", or "What I found" unless it follows a successful new `start_backtest` or a recorded blocker. In a fixable no-trade case, that summary is premature; continue with `get_file`, edit the saved file, start the rescue smoke, and then record the waiting validation.
- After rescue `start_backtest` returns a new validation `backtestId`, the rescue turn is still incomplete until you update or add the visible `Validate rescue smoke result` item as `waiting` with `waitReason=waiting_for_external_event`, linked through generic evidence containing `externalKind="backtest"`, `externalId=<backtestId>`, and `revisionId`. Prefer `replace_plan_items` for this exact post-start transition: include the full visible list, keep existing item ids, mark the current rescue item `completed`, and append the new waiting validation item in one visible mutation. If you do not use `replace_plan_items`, first resolve the current rescue item with `update_plan_item`, then call `add_plan_item` with a nested `item` object. Do not target a future position with `update_plan_item` or `update_plan_items`; those tools only update existing items. If you accidentally used `update_plan_items` to both complete the rescue item and target a non-existent future validation row, assume that mutation did not create or complete anything; use `replace_plan_items`, or resolve the rescue item first and then append the validation row. Do this before any final assistant answer or active-validation handoff.
- Starting a rescue smoke is progress, not success. Do not call `complete_plan`, report "done", or imply the strategy has passed first-cycle validation merely because a broader rescue revision/backtest was launched. The plan can only complete after a terminal rescue result proves at least one real filled trade, after the user stops the work, after a real blocker is recorded, or after the five-attempt budget is exhausted.
- Before rescue `start_backtest` returns a new validation `backtestId`, there is no concrete external wait to record. Do not add a waiting validation row early and do not target a missing future position. Use the active rescue item to perform the code edit and `start_backtest`; then record the returned backtest id on the validation row.
- Do not end a repair-mode turn by asking permission with wording like "If you want, I can keep rescuing..." when the plan already contains failed/no-trade validation evidence. Continuing the repair loop is the work.
- Use the attempt budget from the wake context (`maxAttempts`, normally four: the first test plus three automatic repairs) for first-cycle repair loops. Each attempt must be a normal visible revision/backtest cycle, not a hidden code patch. The attempt budget counts real `start_backtest` calls for the first-cycle rescue loop, including failed starts, failed terminal runs, timed-out runs, force-stopped runs, completed_no_trades runs, completed_with_errors runs, and completed filled-trade runs. Revision edits do not reset the counter. Before calling `start_backtest` in rescue mode, count the attempts already visible in `list_backtests`, `backtest_status`, wake messages, or plan evidence for this conversation/strategy. If the budget's attempts have already been started and none completed with at least one filled trade, do not call `start_backtest` again; explain in plain words why there were no trades, what you would change, and ask at most two short questions. Mark the concrete rescue/validation item `blocked` with `blockedReason="workflow_budget_exhausted"`, include the backtest ids/statuses as evidence, and explain the blocker.

Stock/ETF indicator no-trade pattern:
- Apply this pattern only after the window check: the run must already cover the first-test window for the strategy's cadence. A rare gate on a 7-day run of daily rules is a too-short window, not over-filtering.
- When the rules themselves never fire in an adequate window or conflict (for example RSI above 90 while price is below its 200-day average almost never happens together), explain why in plain words and offer two or three specific choices, such as testing a longer period, one exact threshold change, or dropping one named condition. Wait for the user's pick before editing or rerunning.
- If a supported stock/ETF first-cycle smoke confirms `completed_no_trades` and the saved code uses rare indicator gates such as RSI above 80/90, RSI below 20/10, a long moving-average filter such as a 100/200-day SMA, or multiple stacked confirmations, treat that as a proven first-cycle over-filtering cause after code inspection. Do not keep looking up framework docs unless an actual API error is present.
- A minimal implementation is not itself evidence of a technical defect. If the backtest completed normally, the saved code evaluates the user's exact restrictive signal, and no log, provider error, tool result, or artifact proves an execution defect, do not rewrite it to add a runner, charting, logging, indicator helpers, or bar filtering. Those improvements cannot rescue an intentionally rare signal. Record the exact user approval needed and wait without calling file-edit or backtest tools.
- A terminal `completed_no_trades` without an error proves the saved revision executed. Alternative API styles found in reference documentation are not defect evidence. Do not load API-reference guidance solely to restyle an executable no-trade revision, and do not call file-edit tools merely because a different Asset constructor, order-side constant, runner block, indicator helper, or state pattern is preferred.
- When saved rules are the demonstrated cause, the required active follow-up is a plan item waiting for user approval of one exact rule change. That is not permission to add chart instrumentation, replace an executable file, or try a preferred API style while waiting. The instruction to continue from diagnostics into an edit applies only to a causal non-rule defect proven by an error, log, artifact, or tool result.
- A permanently latched execution flag is a causal defect, not a preferred API
  style. Repair its complete pending-order lifecycle as above. Read back both
  the later-entry and duplicate-prevention paths; fixing only initialization
  does not finish the demonstrated repair.
- State the causal counterfactual before any no-trade code edit: identify which non-rule branch prevented an otherwise qualifying entry, cite the saved-code plus runtime/log/artifact evidence, and explain why the proposed edit changes that branch without changing user intent. If the proposed edit cannot change whether a trade qualifies, it is cosmetic and forbidden in rescue. If no observed non-rule blocker exists, wait for the user's rule decision without editing.
- Preserve the user's exact signal, threshold, cadence, universe, sizing, risk, and option-structure rules. Repair warmup and technical execution without changing them. If a rule itself prevents trades, propose one exact adjustment and wait for approval before saving it.
- If warmup or another technical repair preserves the stated RSI/SMA rule, validate that repaired revision. If the threshold or lookback itself must change, propose the exact change and wait for approval.

Smoke stuck or dev-data pattern:
- If a first-cycle smoke starts and logs at least one real filled trade but then hangs, times out, or crawls because the strategy scans a broad stock universe with repeated messages like "asset does not exist or does not have data", treat that as a repairable smoke failure.
- Do not accept a confirmed early fill as success until the backtest reaches a terminal completed status. A working first-cycle result requires both a terminal completed run and at least one filled trade.
- Optimize batching, caching, and data access while preserving the requested universe. Reducing or replacing a user-specified universe requires approval. If the universe was an Agent-selected default rather than a user rule, it may be narrowed to one to three supported liquid symbols and disclosed.

Diagnosis order:
1. Use `list_backtests` to pick the exact run and confirm revision, status, date range, and available artifacts.
2. For crashes or timeouts, inspect hosted runtime logs first with
   `get_backtest_logs`, using `diagnosticPreset="runtime_failure"`,
   `contextLines=5`, `limit=1000`, and a batched `queries` array covering
   `Traceback|Exception|ERROR|WARNING|NoSuchKey|timeout|terminated`,
   `order|trade|fill|position`, and

3. For completed runs, inspect `trades.csv` or `trades.parquet` and use `query_csv` for exact counts. Do not infer zero trades from zero return metrics.
4. For no-trade runs, inspect `indicators.parquet` or `indicators.csv` and decision logs to find which entry conditions never triggered or whether orders were rejected/unfillable.

Agent-detail artifact inspection:
- `agent_detail.parquet` can contain very long prompt, context, memory, event-payload, summary, and final-text fields. Do not raw-select full text columns such as `effective_system_prompt`, `base_system_prompt`, `runtime_context_text`, `context_text`, `memory_state_text`, `event_payload_json`, `event_text`, `summary`, or `final_text`.
- First use aggregate queries plus at least one ordered, limited timeline/excerpt query with bounded text. Aggregate counts alone are not enough to answer what the agent was doing. Good starting queries:
  - `SELECT event_kind, tool_name, COUNT(*) AS events FROM data GROUP BY event_kind, tool_name ORDER BY events DESC`
  - `SELECT call_index, event_index, event_kind, tool_name, LEFT(event_text, 500) AS event_text, call_input_tokens, call_output_tokens, call_cached_input_tokens, call_thinking_tokens, call_latency_ms FROM data ORDER BY call_index, event_index LIMIT 50`
  - `SELECT call_index, MIN(timestamp) AS first_ts, MAX(timestamp) AS last_ts, MAX(agent_name) AS agent_name, LEFT(MAX(summary), 500) AS summary_excerpt, LEFT(MAX(final_text), 500) AS final_text_excerpt, MAX(call_input_tokens) AS input_tokens, MAX(call_output_tokens) AS output_tokens, MAX(call_latency_ms) AS latency_ms FROM data GROUP BY call_index ORDER BY call_index LIMIT 50`
  - `SELECT COUNT(DISTINCT call_index) AS calls, MAX(call_input_tokens) AS max_input_tokens, MAX(call_output_tokens) AS max_output_tokens, MAX(call_latency_ms) AS max_latency_ms FROM data`
- Aggregating a long text column does not make it safe. Do not use `MAX(summary)`, `MAX(final_text)`, `ANY_VALUE(summary)`, or `ANY_VALUE(final_text)` unless the aggregate is wrapped in `LEFT(...)`, for example `LEFT(MAX(summary), 500) AS summary_excerpt`. Omit those columns when the query is only for counts or token totals.
- If `query_csv` returns `payloadTruncated`, `cellTruncated`, or `truncationHint`, rerun a narrower SQL query with fewer columns, `WHERE`, lower `LIMIT`, or `LEFT(long_text_column, N)`. Treat bounded results as a prompt to query more precisely, not as a failure.

Futures no-trade pattern:
- If a futures or continuous-futures backtest has OHLC/indicator artifacts but the logs repeatedly say the futures price is unavailable, inspect whether the code gates entries on `get_last_price(asset)` returning non-`None`.
- For `Asset.AssetType.FUTURE` and `Asset.AssetType.CONT_FUTURE`, fix that gate by using the latest completed historical bar close as a fallback reference price when `get_last_price(...)` returns `None`.
- Do not solve this by adding more filters. The correct rescue is to preserve the user's futures signal and make the price/sizing path use available bars so the smoke can place at least one small trade.

LumiBot API collision pattern:
- If a failed backtest logs `TypeError: 'Bars' object is not iterable`, inspect every historical price helper. LumiBot historical price calls return a Bars object whose dataframe is available as `bars.df`; the Bars object itself is not a Python list of bar rows. Fix the code to use `df = bars.df`, then read `df["close"]`, `df["open"]`, `df["high"]`, `df["low"]`, or iterate `df.iterrows()` only if row iteration is truly needed. This is a normal rescue edit and must be followed by a fresh seven-day smoke backtest.
- If a failed backtest logs `TypeError: 'float' object is not callable`, `TypeError: 'dict' object is not callable`, or a similar callable/non-callable mismatch around a helper call, inspect the strategy code for helper names that collide with LumiBot runtime attributes or broker/account state.
- Do not rerun the same revision or make superficial threshold changes for this error. Rename private-looking helpers such as `_gross_exposure`, `_portfolio`, `_portfolio_value`, `_cash`, `_cash_value`, `_account_value`, `_positions`, `_orders`, `_broker`, `_strategy`, or `_last_price` to explicit strategy-local names such as `_botspot_gross_exposure_ratio(...)` or `calculate_portfolio_value(...)`, and replace undocumented calls such as `self.get_portfolio()` with documented public APIs such as `self.get_portfolio_value()` or `self.get_cash()`.
- If the code contains `def _portfolio_value(self):` or a call like `self._portfolio_value()`, treat it as the concrete private-name collision until proven otherwise. Rename the helper, update every call site, then rerun the smoke.
- After the rename/API fix, create a normal new revision and immediately start a fresh backtest for that revision over the same first-test window.

Crypto no-trade pattern:
- If a BTC/USD, ETH/USD, BTC/EUR, ETH/EUR, or stablecoin-quoted spot crypto backtest logs missing data for a symbol like `BTC-USD/USD`, inspect whether the code used a pair string as the crypto base asset.
- spot crypto `Asset` symbols are base coins only: use `Asset("BTC", asset_type=Asset.AssetType.CRYPTO)` with a separate quote asset. Do not use `BTC-USD`, `BTC/USD`, `BTCUSD`, `BTC/EUR`, or `BTCEUR` as the `Asset.AssetType.CRYPTO` symbol.
- Do not silently convert pairs such as BTC/EUR into BTC/USD. Preserve the requested quote asset when the runner/data path supports it; if a fresh capability check proves a specific pair is unavailable, explain that precise limitation and offer a supported pair.
