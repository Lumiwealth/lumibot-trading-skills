# Existing Strategy Edits

Use saved-file inspection and file tools when the user asks for a meaningful strategy change, bug fix, rewrite, or behavior change.

Always read actual saved code before editing. Preserve intent/name unless the user asks to change them. Load focused skills before broad corrections.

For market-data performance edits, after that saved-file read load
`lumibot-api-reference` and its `references/scanner-performance.md`; use
`references/quote-snapshot-example.py` for the complete bounded reader.
Checking the batch API signature alone misses the caller's error boundary:
one malformed member can raise for the whole batch. Preserve healthy contracts
with bounded failure isolation instead of a bare bulk call or dropping the
whole failed batch. Keep symbol guards and viable-decision order reads fresh;
a scan-wide order cache changes which trades are blocked. These are part of
preserving the existing scanner, even for a request phrased only as batching.

Never claim fixed if a file tool fails; refresh the file/edit handle and retry with a successful file edit before starting validation.

An ambiguous text match is a recoverable editing error, not a task blocker.
After refreshing the saved file, change the next mutation to verified
`replace_range` operations with exact `expectedOldText`, or `replace_file` with
the complete current file plus the scoped correction. Do not submit the same
ambiguous `oldText` again inside a larger batch. If exact ranges are not known,
use the complete-file route instead of guessing ranges or ending the turn.
The rejected batch saved no operations. Continue to a successful revision and
readback while a supported editing route remains; acknowledging two rejected
patches does not complete an authorized code change. A denied write, unavailable
tool, unresolved concurrent change or actual exhausted budget is a different
condition and must be reported accurately.
